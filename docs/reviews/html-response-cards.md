## Acceptance and boundaries

- Only an explicit, closed assistant `wks-html-card` fence containing a valid v1 JSON object mounts a card, and only with an owning chat context. The envelope has a 64 KiB UTF-8 limit, at most eight actions, and required useful fallback text. Multiple cards render independently. Unknown versions/actions, malformed JSON, incomplete fences and oversized payloads remain readable without mounting.
- Transcript bytes, replay format, provider events and persistence are unchanged. Other clients retain the original JSON fence and its fallback. User messages and ordinary/tool Markdown do not opt into the assistant rendering context.
- DOMPurify provides maintained HTML sanitization with a restrictive element/attribute allowlist. Model scripts, handlers, navigating/resource attributes, forms, metadata and embedded documents are removed. The opaque `srcdoc` iframe has only `sandbox="allow-scripts"`. Host CSP precedes generated bytes; the only permitted script nonce belongs to the fixed host runtime. Local expansion, filtering and sorting are declarative.
- CSP blocks resource-bearing CSS, including imports, URLs and escaped forms. The browser may report a request event for a CSP-blocked resource; the harness requires the explicit CSP failure and zero off-origin routing, with a successful same-origin observation control. Sandbox alone does not prevent a script from navigating its own frame: removing generated navigation and allowing only the fixed host script are necessary parts of the boundary.
- `postMessage` only accepts height reports from the exact iframe window, clamps finite numeric heights to 40–560px, and has no action dispatch path. Host action buttons display trusted visible verbs outside the iframe. An accessible Text alternative disclosure remains available on successful cards.
- `open_worker` rechecks the live local owner and target identity, direct parent relationship, ended/foreign states and current pane identity. `fill_composer` addresses the owning session AND pane, preserves the existing draft, focuses the composer and never sends.
- `view_diff` uses one guarded main-process IPC and an inline `DiffView`. Main derives cwd from the live owning session, reads a bounded regular-file descriptor, verifies canonical containment and inode identity before bytes are read, and rechecks the owner before returning. HEAD is compared with the exact working file; untracked files are additions. **Cards never enter ReviewPane's fuzzy basename selection or the ordinary untracked Git byte-read path.** Those unrelated flows retain their behavior. The competing implementations were consolidated into this single path in `gitService.ts`.
- The product bundles SKILL.md plus schema, interaction reference and three examples. Installation uses project `.claude/skills` or `.agents/skills`, never personal global roots; existing edited skills, symlinks and disabled markers are preserved. A versioned project-owned copy plus a short existing instruction-channel pointer handles collisions and other adapters. There are no native-discovery claims for other harnesses.

## Limits of the evidence

The browser harness exercises actual production renderer components, with fixture transcript/owner context, in standalone Chromium. IPC/spawn tests capture production handlers and payloads with mocked services; native discovery uses real CLIs with a mock model endpoint. No installed Electron launch, live daemon transport, remote host diff support, real-model card generation or non-Linux native-discovery run was verified. Skill discovery does not promise automatic model selection on every prompt. Other-client/replay compatibility follows the unchanged transcript representation and renderer replay tests, not a separate running client.

Card diffs are HEAD-to-working-file snapshots of existing text files, limited to 256 KiB per side. Deleted, binary, oversized, unresolvable and non-repository targets refuse gracefully; there is no staged-only/history selector. Native Windows/macOS descriptor behavior still needs platform runtime coverage. Independent deep review and the manager's local merge remain subsequent steps.
