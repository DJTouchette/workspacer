# Claude usage bar flickers because FRESH_FOR_SECS (5min) is shorter than IDLE_INTERVAL_SECS (15min)

## Observation
The Claude 5h/7d meter blinks off mid-run because claudemon's account reading goes stale faster than it is refreshed, and the percentage it supplies is injected per-render rather than persisted. Four composing facts: (1) the stream transport's `rate_limit_event` carries `resetsAt` WITHOUT `utilization` (only warning-threshold events carry the percent), so `UsageAcc` accumulates a reset time but never a `five_hour_pct`; (2) `SessionStore::patch_rate_limits` (store.rs:1122) overlays the account reading onto the outgoing StatusLine and does NOT write back into `UsageAcc`, so every `build_status_line` rebuild starts from a pct-less accumulator; (3) that overlay is gated on `AccountUsage::is_fresh`, `FRESH_FOR_SECS = 5*60` (account_usage.rs:53); (4) `IDLE_INTERVAL_SECS = 15*60` is THREE TIMES that ceiling, and `spawn_poller` never re-arms a root's booked next-attempt when it transitions idle->live (the delay is written only after a poll runs, using the `is_live` value at that instant). So a root polled while idle is booked 15 minutes out; a session started a minute later gets one patched status line, then every rebuild for the next ~13 minutes drops `five_hour_pct` and the meter empties. `build_status_line` stamps `received_at: now` unconditionally (providers/mod.rs:782), so that pct-less line is the NEWEST reading the renderer sees and displaces the good one in `RateLimitCard`'s `lastRateLimit` cache — the card survives (it still has `fiveHourResetsAt`) but the filled bar does not. Verified live 2026-09-02: 99 daemon session rows, only the single live one carries any window; `GET /usage/report` answered `observed_at` 26s old, five_hour ok at 8%. Separately confirmed: the poller's old live-sessions-only gate was already fixed (46fd339f), and the upstream OAuth endpoint really does report `utilization: 0.0, resets_at: null` for a window that is not running (the `nimbus_quill` bucket in the live capture shows exactly that shape) — which the hub's `ReadWindow` correctly calls `no-reset-time-reported`, but which the desktop bar never sees because no renderer surface reads `/usage/report`.</observation>
<parameter name="impact">This is the user-reported "usage bar comes and goes". It is a claudemon defect, not a renderer one — the renderer gating (OverviewPane.tsx:181 returning null with no live session) is a separate, already-documented cold-start gap that explains blankness after a restart but cannot explain a bar that flickers while the app stays open. Any poll failure re-opens the same hole at up to the 1-hour MAX_BACKOFF_SECS, with the stale reading deliberately retained.</impact>
<parameter name="recommendation">Nothing currently ties FRESH_FOR_SECS to the poll cadence — add a static assertion that FRESH_FOR_SECS >= IDLE_INTERVAL_SECS, and re-arm a root's schedule entry when it goes idle->live. `poll_cadence_backs_off_and_is_capped` tests `next_poll_delay` in isolation and never relates it to freshness. When a usage window is missing, check `patch_rate_limits`'s freshness gate BEFORE looking at the renderer: the percentage is not persisted anywhere, so it is absent from any status line rebuilt outside the 5-minute window.
