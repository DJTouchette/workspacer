## Guidelines

Why these files are risky (clusters, not isolated files):

- **Config cluster** (`useConfig.ts`, `configService.ts`): `config.yaml` has **two writers** — the desktop TS `configService` and the brain (Go). Both must mtime-gate writes or they clobber each other (this caused a reset bug). Defaults are single-sourced from `config_defaults.json` (go:embed'd + generated TS) — don't hardcode defaults in either writer.
- **Session cluster** (`claudeSessionStore.ts`, `types/claudeSession.ts`, `state.rs`): the session snapshot type has fan-in 45 — nearly every card/pane renders from it, so shape changes ripple everywhere. Daemon keeps dead sessions as resumable `Stopped` rows (200, not 404); desktop aliveness = hook store minus status `ended`. `state.rs` is claudemon's authoritative session state; keep it and the TS store in agreement.
- **Pane/IPC boundary** (`types/pane.ts`, `ipcChannels.ts`, `ipcTypes.ts`): new `PaneType`s must be added to the **exhaustive `Record` maps** or the build/type-check fails by design. IPC goes through a typed registry — add both the channel and its type together.
- **`App.tsx`**: highest churn (57), low fan-in — it's the wiring root. Risky because it changes constantly, not because many things import it. A 2026-07-30 decomposition audit concluded the size is mostly *irreducible orchestration* (~400 lines JSX + 20+ hooks wired through ~64 useCallbacks); the extractable parts were small pure policies and are already out (`apps/desktop/src/renderer/src/lib/hibernation.ts` + `useBrowserHibernation`/`useSessionSnapshots` hooks, `textScale.ts`). Don't plan another "split App.tsx" pass expecting big slabs to move.
- **Federation widened two seams (2026-08-16)**: `apps/desktop/src/main/ipc.ts` now routes per-session calls by hub (`hub:<peer>/<method>`), and `apps/desktop/src/renderer/src/backend/webBackend.ts` carries its own `sessionHub` qualify layer — new per-session methods added to either without hub-awareness silently act on the wrong machine.

When modifying any file listed above:
- Check the fan-in count — that many files depend on this module
- Run the full test suite, not just the file's own tests
- Consider using `recon related <file>` to find affected files
- **`make test` does NOT run the CI format/lint gates.** CI additionally runs, per stack: desktop = config-defaults codegen drift + `prettier --check` + `tsc --noEmit` (tsconfig.main.json AND src/renderer); tui/claudemon = `cargo fmt --check` + `cargo clippy --all-targets -D warnings`; hub = gofmt + go vet. Run the equivalent sweep before pushing, or a green `make test` still fails CI.
