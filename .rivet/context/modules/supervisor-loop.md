# Supervisor loop: /supervise skill + coordinator/summarizer workers

## Overview
A "fleet supervisor" is a normal Claude Code session spawned with `supervisor: true`. On spawn, workspacer installs a real Claude Code skill (`~/.claude/skills/supervise/SKILL.md` + a bundled `fleet.mjs` script) that the coordinator invokes as `/supervise` and re-runs on a loop, polling every other agent, spawning a cheap summarizer worker to digest transcripts, and calling `mcp__workspacer__*` tools to act (spawn/message/notify/approve/answer). `supervisorNudge.ts` wakes a live supervisor early — with a `[supervisor]`-prefixed message — the instant another agent blocks, instead of waiting for the poll interval.

## Key modules
- `apps/desktop/src/main/services/supervisorSkill.ts` — owns `SKILL_BODY` (the SKILL.md markdown, frontmatter `name: supervise`) and `FLEET_SCRIPT` (the `fleet.mjs` source, zero-dep, talks to claudemon's REST API at `http://127.0.0.1:7891` by default, overridable via `CLAUDEMON_API_URL`); `installSupervisorSkill()` writes both idempotently (`writeIfChanged`, no-op if content unchanged) into `~/.claude/skills/supervise/`; `ensureSupervisorHome()` creates/returns `~/.workspacer` (with a README) as the default cwd for supervisors with no explicit cwd.
- `apps/desktop/src/main/services/supervisorNudge.ts` — `SupervisorNudge.onBlock(session, kind, supervisorIds)` coalesces (1500ms, `COALESCE_MS`) blocked-agent notices per supervisor and delivers one `[supervisor] An agent is now blocked...` message via `claudemonSessionClient.message()`; never nudges a supervisor about its own block; a rejected send (supervisor ended) is swallowed.
- `apps/desktop/src/main/services/claudeSpawn.ts` (around line 113-153) — the PTY Claude spawn path: calls `installSupervisorSkill()` and defaults `model` to `configService.getConfig().supervisor.model` only when `opts.supervisor`; builds argv via `facadeSpawnArgs(...)` when `wantsFacade` (`opts.supervisor || opts.mcpFacade`); opens `ensureSupervisorHome()` as cwd when no explicit cwd given.
- `apps/desktop/src/main/services/mcpConfig.ts` — `SUPERVISOR_SYSTEM_PROMPT`, `MCP_FACADE_URL` (`http://127.0.0.1:7897/mcp`), `facadeSpawnArgs()` (builds `--mcp-config` + `allowedTools: ['mcp__workspacer']` + `appendSystemPrompt` that names `parentSessionId`, kicks off `/supervise`, and parameterizes the summarizer model + `pollSeconds`, default 45 / fallback model `sonnet`), and `managedFacadeInstructions()` used for non-Claude / stream-Claude managed spawns.
- `apps/desktop/src/main/services/managedSpawn.ts` — the hub-bus / managed-provider spawn path (`spawnManagedAgent`, `spawnCodexHybrid`); also opens `ensureSupervisorHome()` for supervisors but injects role text via `managedFacadeInstructions(!!opts.supervisor)` passed as `instructions` to `claudemonSessionClient.spawnManaged` — it does **not** call `installSupervisorSkill()`.
- `apps/desktop/src/main/services/claudeSessionStore.ts` (lines ~494-504, ~563-573) — the two ambient-state transition sites (Claude hook path and `applyManagedMode` for managed providers) that call `supervisorNudge.onBlock(session, 'approval'|'question', this.supervisorSessionIds())` when a session newly enters `waiting_approval`/`waiting_input`.
- `apps/desktop/src/main/services/mcpFacadeDaemon.ts` — spawns/health-checks the Go MCP facade binary (`services/hub/cmd/mcp`), a thin adapter that forwards every `mcp__workspacer__*` tool call over the hub bus as a capability `call`, executed by `apps/desktop/src/main/services/hubCapabilities.ts` in the Electron main process.
- `services/hub/cmd/mcp/main.go` — registers the actual tool set the skill depends on: `list_agents`, `get_transcript`, `get_snapshot`, `spawn_agent`, `send_message`, `approve`, `answer`, `get_config`, `notify`, etc.
- `apps/desktop/src/main/services/configService.ts` (~line 140) — `supervisor: { model, summarizerModel, pollSeconds }` config shape read by `claudeSpawn.ts`/`facadeSpawnArgs` and restated in the skill's step 0 as a fallback (`sonnet` / `45`).

## Failure modes
- `installSupervisorSkill()` is wrapped in try/catch and is explicitly best-effort: on failure the supervisor "falls back to its system prompt / the MCP tools" — the loop still nominally works via `SUPERVISOR_SYSTEM_PROMPT` + `appendSystemPrompt`, but without the `/supervise` procedural steps or `fleet.mjs`.
- `fleet.mjs` itself has no retry: any non-2xx from claudemon (`getJSON` throws `<path> -> HTTP <status>`) or a fetch failure propagates to a `console.error` + `process.exit(1)`; the supervisor sees a Bash tool error, not a structured response, and must reason about it itself.
- `supervisorNudge.send()` swallows all errors from `claudemonSessionClient.message()` — a supervisor that has just ended silently drops the nudge; no visible error, no retry.
- The skill only self-loops by re-invoking `/supervise` (or preferring the `/loop` skill) — nothing in the app code enforces the poll cadence; if the coordinator ignores the instruction (context pressure, model drift) the loop simply stops with no external watchdog other than `supervisorNudge`'s event-driven wake on the next block.
- `supervisorNudge.onBlock` reads `this.supervisorSessionIds()` at call time — if a supervisor session id changes list membership mid-coalesce window, the nudge still targets whatever was live when the timer fires (1500ms `COALESCE_MS`), not re-checked at send time.

## Gotchas
- **PTY-only skill install**: only `claudeSpawn.ts` calls `installSupervisorSkill()`. `managedSpawn.ts` (which also handles `provider === 'claude', transport === 'stream'` — i.e. headless/stream-transport Claude supervisors) never installs the skill; those supervisors rely solely on `managedFacadeInstructions(true)` text, which does **not** mention `/supervise` or `fleet.mjs`. A supervisor spawned via the stream transport or a non-Claude managed provider effectively never gets the real skill file.
- `FLEET_SCRIPT` is written "deliberately free of backticks, `${...}` and backslash escapes so it survives verbatim inside this template literal" (comment at `apps/desktop/src/main/services/supervisorSkill.ts:141-142`) — editing it must preserve that constraint or the outer JS template literal in `apps/desktop/src/main/services/supervisorSkill.ts` breaks.
- `writeIfChanged` means skill files are only rewritten when content differs — bumping `SKILL_BODY`/`FLEET_SCRIPT` ships automatically on the next supervisor spawn (no explicit version field), but a user's own hand-edits to `~/.claude/skills/supervise/SKILL.md` are silently clobbered the moment content diverges from the current constant.
- `fleet.mjs` talks directly to claudemon's REST API (`/sessions`, `/sessions/:id/conversation`) — it bypasses the MCP facade entirely, so the daemon's REST endpoint shapes (`status_line.context_used_pct`, `pending.kind`, conversation `items[].kind` in `{user_message, assistant_text, tool_use, tool_result}`) are an implicit contract this script depends on; a daemon response-shape change silently breaks `status`/`convo`/`reply` parsing (errors surface only via `process.exit(1)`).
- `SKILL_BODY` explicitly instructs the coordinator to check for `mcp__workspacer__*` tools and "stop" if absent — the skill is inert (by design) outside a real supervisor session; don't assume its presence in `~/.claude/skills/` implies a live supervisor.
- Two independent system-prompt-injection paths must stay conceptually in sync: `facadeSpawnArgs()` (PTY, `appendSystemPrompt`) drives the coordinator into `/supervise` and passes `summarizerModel`/`pollSeconds`; `managedFacadeInstructions()` (managed/stream) reuses `SUPERVISOR_SYSTEM_PROMPT` but has its own hand-written loop text with no cadence parameter — changing supervisor behavior often requires editing both plus `SKILL_BODY`.
- The digest worker spawned per `SKILL_BODY` step 1 uses `mcpFacade: true` (not `supervisor: true`) — it gets the facade tools via the non-supervisor branch of `facadeSpawnArgs`/`managedFacadeInstructions`, explicitly told not to spawn or coordinate other agents; conflating the two flags would let a "cheap" worker become a second coordinator.
- `ensureSupervisorHome()` and `installSupervisorSkill()` are both used by two independent spawn entrypoints (`ipc.ts` for local Electron IPC spawns, `hubCapabilities.ts`/`managedSpawn.ts` for hub-bus spawns) — the comment in `apps/desktop/src/main/services/supervisorSkill.ts` flags this ("Shared by both spawn paths"); keep both paths calling the same functions rather than duplicating cwd/skill logic.

## Hand-authored notes (2026-08-15) — tool tiers reached the supervisor

- **Summarizer/digest workers now spawn with `toolScope: "view"`** (`supervisorSkill.ts` ~L73 and the coordinator prompt in `mcpConfig.ts`): a worker gets only the read-only facade tools (transcripts, snapshots) instead of the full operator surface — the old "worker must not become a second coordinator" rule is now enforced by the facade tier, not just prompt text.
- **`SUPERVISOR_SYSTEM_PROMPT` slimmed to role + "call help first."** The per-tier `help` tool (`services/hub/cmd/mcp/help.go`) renders usage guidance from the live tool registry, so the old hand-written tool prose (which used to drift from the actual surface) is gone. Changing supervisor tool guidance now means editing help topics, not the prompt constants. See `modules/mcp-tool-facade.md`.
