# Hub Plugin System: Manifest, Capability Scoping & Sandboxing

## Overview
The `plugin` package loads polyglot sidecar plugins (or sidecar-less webview-only plugins) from `plugin.json` manifests, supervises their processes, and mints scoped bus tokens so each plugin gets exactly the capabilities/paths it declared — never more. It is a second security boundary layered on top of the bus's control-plane token model (`services/hub/internal/bus/bus.go` `RegisterPluginToken` (L227)), sharing a small dependency-free vocabulary (`Grant`, `EventGrants`, `IsPathScoped`) via `services/hub/internal/capspec/capspec.go` so the loader (validation) and the bus (enforcement) can never drift apart. A third, independent layer — `services/hub/internal/sandbox/sandbox.go` — confines what a sidecar *process* can do at the OS level (filesystem writes), separate from what it's allowed to *ask the bus* to do.

## Key modules
- `services/hub/internal/plugin/manifest.go` — `Manifest` struct, `Capability` (verb-only or `{method,paths}` path-scoped), `Validate()` (apiVersion gate, path-scoped capabilities must declare `paths`), `Load`/`LoadDir`.
- `services/hub/internal/plugin/manager.go` — `Manager`: lifecycle (`Add`/`Remove`/`SetEnabled`/`Stop`/`List`), `grantsFor`/`grantsWithBindings`/`expandScope` (manifest capabilities → `capspec.Grant`), `PaneToken`/`RevokePaneToken`/`revokePaneTokensFor` (ephemeral per-pane tokens), `sandboxSidecar` (OS confinement decision + launch).
- `services/hub/internal/plugin/install.go` — `Install`/`InstallFromDir`/`Inspect`: GitHub tarball fetch, extraction (zip-slip guard + decompression-bomb bounds), `runInstall` (unconfined build step), `.install-source` bookkeeping.
- `services/hub/internal/plugin/settings.go` — `GetSettings`/`SetSettings`/`mergedSettings`/`settingsEnvJSON`: manifest-default + `.settings.json` overlay, `WKS_SETTINGS` env injection into sidecars, restart-on-change via `Add`.
- `services/hub/internal/sandbox/sandbox.go` — `Wrap`/`Decide`/`Policy`: bwrap (Linux) / sandbox-exec (macOS) write-root confinement; `Mode` off/best-effort/enforce.
- `services/hub/internal/capspec/capspec.go` — shared `PathParam`/`IsPathScoped`/`Grant`/`EventGrants`; single source of truth for which capability methods are filesystem-scoped.
- `services/hub/internal/bus/bus.go` — `Server.RegisterPluginToken` (L227) / `UnregisterPluginToken` (L291), the bus-side enforcement counterpart consumed by `Manager` via the `TokenRegistrar` interface.

## Failure modes
- **apiVersion mismatch is fatal at load, not a warning**: `Manifest.Validate()` rejects any `apiVersion != APIVersion` ("1"); `LoadDir` collects it into the per-plugin error slice so one bad manifest doesn't sink the batch, but that plugin never loads (no partial/degraded load).
- **Sandbox refuse in enforce mode**: `sandboxSidecar` returns `run=false` when `sandbox.Decide` yields `Refuse` (enforce mode + no bwrap/sandbox-exec on the platform) — the sidecar silently never starts; only a `plugin.sandbox.refused` bus event and no process. Windows has no mechanism at all, so `enforce` mode always refuses sidecars there.
- **Best-effort silently runs unconfined**: default mode; if no sandbox mechanism is available it still runs the sidecar (with only a `log.Printf` WARNING and a `plugin.unsandboxed` event) — easy to miss in production.
- **Settings validation is all-or-nothing**: `SetSettings` validates the entire partial map before writing anything; an unknown key or type mismatch on *any* entry rejects the whole call and persists nothing (no partial writes), but a caller must re-read `GetSettings` to know what actually landed.
- **Best-effort token/file writes**: `loadOrCreatePluginToken` and the `.install-source` write in `install.go` are best-effort — a write failure still returns a usable in-memory value/token, logged loudly for the bus token case but silently swallowed (`return m, nil`) for `.install-source`.
- **PaneToken race (fixed, but load-bearing)**: `PaneToken` registers on the bus and records into `m.paneTokens` under one hold of `m.mu` specifically to close a race with `Remove` — see the extensive comment in `manager.go` and `TestPaneTokenRegisterRecordAtomic`; touching this ordering reopens an unrevocable grant leak.

## Gotchas
- **Static token vs pane token are different trust levels.** `grantsFor(mf)` (used by `Add` for the persisted per-plugin token, stable via `.bus-token`) resolves only `${pluginDir}`; any `${agentCwd}`-scoped capability resolves to *no* roots at static load (fail closed) and only gets real filesystem reach when `PaneToken(pluginID, bindings)` is minted per open pane with `{"agentCwd": ...}`. Never assume the static token has the same reach as an open pane's token.
- **Unscoped fs capabilities are a load-time rejection, not a runtime deny**: `capspec.IsPathScoped` + `Manifest.Validate` reject a filesystem-scoped capability (`fs.*`, `search.project`) declared without `paths` at manifest load — but this depends entirely on `capspec.PathParam` staying exhaustive; a new `fs.*`/`search.*` method added to the bus without a `PathParam` entry bypasses this check (see `capspec.MissingSpec` — there is a build-time cross-check test intended to catch this, don't skip it when adding capability methods).
- **`${...}` token expansion fails closed by design** (`expandScope` in `manager.go`): unknown/unbound tokens and relative paths yield `""`, dropped from `FSRoots`. This means a typo'd token silently grants nothing rather than erroring — good for safety, bad for plugin-author debuggability.
- **Reload/disable must sweep pane tokens.** `Add`'s replace branch (reload/`SetEnabled`) calls `revokePaneTokensFor` — without it, disabling a plugin or reinstalling with reduced capabilities leaves already-open webviews holding the OLD, broader bus grants (regression covered by `TestReloadSweepsPaneTokens` in `services/hub/internal/plugin/panetoken_test.go`).
- **Sandbox confines writes only, not reads or network** (`services/hub/internal/sandbox/sandbox.go` header comment): a sidecar can still read-and-exfiltrate anything readable and always reaches the bus over loopback. A plugin needing full confinement should ship `ui`-only (webview, no `server`) — with nothing arbitrary to execute, capability scoping alone fully confines it; this is the intended escape hatch for the "sandbox escape via fs-scope" hazard, not a stronger sandbox mode.
- **Install's `runInstall` step is intentionally unconfined** — full user privileges, 5-minute timeout only, no sandbox — a deliberate trusted-install (VS Code-extension-like) trust model distinct from the sidecar-runtime sandboxing above; do not conflate the two when reasoning about "is this plugin sandboxed."
- **Settings-env twin structure**: `mergedSettings` (defaults + `.settings.json` overlay) feeds both `GetSettings` (API reads) and `settingsEnvJSON` (`WKS_SETTINGS` sidecar env) — they must stay derived from the same function or defaults/overlay can drift between what the UI shows and what the sidecar receives; `SetSettings` re-`Add`s the plugin (restarting the sidecar) specifically because the sidecar only reads `WKS_SETTINGS` at spawn.

## Hand-authored notes (2026-08-15) — plugin agent tools

- **Plugins can contribute MCP agent tools.** `plugin.json` gained `tools: [{name, description, inputSchema, method}]`; `manifest.go`'s `validateTool` requires each tool's `method` to be covered by the manifest's consent-pinned `provides` list — a tool can never invoke a method the user didn't already consent to the plugin providing. `Manager.ConsentedTools()` (manager.go) is the consented surface, served by the hub-local `plugins.tools` RPC (capspec-classified inert), polled by the MCP facade every 15s and grafted onto per-session servers as `<sanitized_full_plugin_id>_<name>` — **strictly opt-in per session token** (`pluginTools` spawn option; `"*"` = all). Facade side: `modules/mcp-tool-facade.md`.
- **Sidecars answer via `provide()`.** `services/hub/cmd/hub/sdk.js` (and the jira plugin's vendored `wks.js`) gained `provide(method, handler)`: registers the method on the bus and handles inbound `op:"call"` frames; registrations are re-sent on every reconnect. The Jira plugin 1.4.0 (../workspacer-plugins) is the flagship (issue search + detail tools; credentials stay in the sidecar's `WKS_SETTINGS`, the agent never sees them). Gotcha found there: two settings with the same key (`jql`) silently collide — fixed by renaming to `projectJql`; manifest setting keys must be unique.

## Hand-authored notes (2026-07-23)

- **Secret settings** (`SettingDef.Secret bool`, `"secret": true` in plugin.json — a FLAG on type string, not a new type, so old hosts degrade to a plain input instead of rejecting the manifest). Contract in internal/plugin/settings.go: plaintext at rest (0600 overlay) and in the sidecar `WKS_SETTINGS` env ONLY; every read surface (`GetSettings`, `SetSettings` echo, `plugin.settings.changed` broadcast, webview `__WKS_SETTINGS__` via settingsFor→GetSettings) reports `SecretPlaceholder` (`"__WKS_SECRET__"`, mirrored as TS `SECRET_PLACEHOLDER` in types/plugin.ts — keep in sync). SetSettings drops sentinel-valued secret keys (echo = unchanged); `""` clears. Validation: secret ⇒ string + no non-empty default (manifest listing is public). Desktop: `SecretInput` in PluginsSection.tsx — write-only password field, commits on blur/Enter (NOT per keystroke — every save restarts the sidecar). The settings-env twin structure is now deliberately forked: `mergedSettings` stays raw; redaction happens at GetSettings/SetSettings, never inside mergedSettings (or the sidecar would get masked tokens).
