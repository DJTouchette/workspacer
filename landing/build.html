building from source

This page is for people building work{spacer} from the repo or extending it. If you just want to use it, the operational docs are what you want.

work{spacer} is a monorepo. Four Rust components are the product, and one older app sits beside them:

  • apps/native: the native app, wks-native. A GPUI window with no webview in it. This is the product.
  • services/hub-rs: the hub. The event bus, the capability router, the shared services, the plugin system and the MCP facade. It builds as a library (the workspacer-hub crate) and as the workspacer-rust executable, installed under the name workspacer.
  • services/claudemon: the session engine. It owns agent sessions, PTYs and the per-provider adapters. Also a library and a claudemon executable.
  • apps/tui: wks-tui, a terminal client on the same bus.
  • apps/desktop: the Electron app. On its way out: this release ships it alongside the native app and the next release deprecates it, so new work goes into the native app. Everything about it lives in its own section at the end of this page.

The root Makefile is the single entry point; every target delegates into the right component directory.

toolchains

  • Rust, a current stable toolchain through rustup. It is not pinned, and it is all the native app, the hub, the engine and the TUI need.
  • Node 22, pinned by mise in mise.toml. Only the Electron app needs it, plus the script that packages the native Windows installer.
  • Go 1.25, also in mise.toml, only for an optional historical test oracle. Nothing that ships is Go; see scripts/reference/README.md.

The native app links against system libraries. On Debian or Ubuntu:

sudo apt-get install libxkbcommon-dev libxkbcommon-x11-dev libfontconfig1-dev \
  libwayland-dev libssl-dev libasound2-dev libvulkan1 mesa-vulkan-drivers

Linux also needs a working X11 or Wayland display and a Vulkan driver. macOS needs Xcode's command-line tools. Windows needs the MSVC Rust toolchain and the Visual Studio C++ build tools.

run the native app

make dev-native-local     # debug build, then the window with its own backend
make run-native-local     # the same, as a release build
make build-native         # just build apps/native/target/release/wks-native

The -local targets start wks-native --local: the window owns the hub and the session engine in its own process, so there is nothing else to build or start first. No Node, no Go, no separate daemon.

make dev-native           # debug build, attached to a hub that is already running
make run-native           # the same, as a release build

Without --local the app is only a client. It connects to ws://127.0.0.1:7895/bus unless you point it elsewhere, and it never owns or stops the backend it attached to. Every target passes ARGS through:

make dev-native-local ARGS="--keep-running"     # closing the window minimizes instead of quitting
make dev-native ARGS="--bus wss://host/bus --token-file /path/to/token"
make dev-native ARGS="--demo"                   # fixture sessions; no agents, credentials or model calls

build the backend by itself

make build-cli            # services/hub-rs/target/release/workspacer-rust
make build-hub            # the same target under its older name
services/hub-rs/target/release/workspacer-rust serve

serve is the whole backend in one process: session engine, bus, services and MCP facade. It needs no sibling binaries. Installed releases expose the same executable as workspacer, so the command reads workspacer serve there. make build-claudemon builds the engine's standalone executable (services/claudemon/target/release/claudemon), which the native app and serve do not need: they link the engine as a library.

run the tui

make dev-tui              # wks-tui, debug; builds the Rust backend and claudemon first
make run-tui              # wks-tui, release

The TUI is a bus client by default and starts a local Rust backend if none is running. ARGS="--direct" skips the bus and talks to claudemon's own API instead.

test

make test-native          # native UI and protocol tests, plus the embedded-engine lifecycle test
make test-hub             # cargo test for services/hub-rs
make test-claudemon       # cargo test for services/claudemon
make test-tui             # cargo test for apps/tui
make test                 # all of the above, plus the Electron app's suites

From apps/native, cargo test --locked --no-default-features runs the core and protocol suite with no display and no GUI libraries, which is the fast loop while you work on the model or the bus client.

package

make package-native-linux # apps/native/target/package/workspacer-native-<version>-linux-<arch>.tar.gz

That is a release build packed with a per-user installer (install.sh, into ~/.local) and a checksum beside the archive. The Windows installer is built by apps/native/scripts/package-windows.mjs and needs Node 22 and NSIS; apps/native/README.md has the exact steps. There is no macOS package, because an app bundle needs signing and notarization that are not set up.

per-component builds

Every component also builds on its own from its directory; the make targets just delegate. The component READMEs go further than this page: apps/native/README.md, apps/tui/README.md, services/claudemon/README.md, and for the hub services/hub-rs/MIGRATION.md.

make build                # every component, the Electron app included
make clean                # remove build artifacts across all components

architecture internals

There are two halves: a backend that owns the agents, and clients that show them. The native app is a client that can also carry the backend inside it.

the pieces

  • the hub (services/hub-rs, Rust). One runtime that owns the bus (a WebSocket at /bus), the capability router, the shared services behind those capabilities (sessions, spawning, git, files, jobs, plugins, federation), the phone and web clients it serves, and the MCP facade. As a standalone process it binds 127.0.0.1:7895, with the facade on 127.0.0.1:7897.
  • the session engine (services/claudemon, Rust). It owns the sessions: per-session state, PTYs, the per-provider adapters, and a structured conversation so a client reads messages and tool calls instead of raw scrollback. Standalone it listens for Claude Code hook events on 127.0.0.1:7890 and serves REST + SSE on 127.0.0.1:7891. That API is documented in full on build a client.
  • clients. wks-native, wks-tui, the phone client the hub serves at /m, any MCP client, and the Electron app. They all speak the same bus, so a session started in one can be watched and driven from another.

three ways it runs

  • wks-native --local. The app starts the same hub and engine as a library, on a dedicated OS thread with its own Tokio runtime, never on the UI thread. The UI sends bounded, typed commands and reads the latest immutable view through a watch channel. State lives in Workspacer Native Rust Preview under the platform's local-data directory (or wherever --rust-local-dir points), and the listeners take loopback ports the OS hands out rather than the fixed ones above (the bus remembers the one it first got, so a shared link keeps working across restarts). Closing the window quits unless --keep-running is set, and quitting joins the hub and the engine before the process exits, including the provider processes they own.
  • workspacer serve. The same backend with no window: one process owning the engine, the bus, the services and the facade. --hub-only starts the control plane without an engine, and --external-claudemon lets a hub-only server borrow a daemon someone else owns. This is what runs on a box with no desktop.
  • wks-native with no flag, or --bus. A client and nothing else. It attaches to a hub that already exists and leaves that hub running when it exits.
If you remember three processes. Earlier versions of this page described an Electron app supervising two daemons, a Go hub, a separate brain provider and a private Node companion. The Go hub, the brain and the companion are gone from the tree: the Rust hub owns their jobs in one runtime. The Go source survives only as a pinned historical checkout used as a test oracle (scripts/reference/README.md). The Electron app is still here for one more release, and described below.

the hub bus

Each client opens one bidirectional WebSocket to ws://<addr>/bus and exchanges JSON frames. Publish and subscribe share the same pipe, unlike the engine's SSE-down / POST-up split, because it keeps plugins simple. The frames and topic matching live in src/protocol.rs; the bus actor and the router in src/runtime.rs.

Pub/sub. Subscribe to topics, publish events:

client → hub:   {"op":"subscribe","topics":["agent.*"]}
                {"op":"publish","event":{"type":"myplugin.tick","source":"myplugin","data":{...}}}
hub → client:   {"op":"event","event":{...}}

Topic patterns are exact (agent.snapshot), namespace wildcard (agent.*), or all (*). The event envelope is { id, type, source, time, data }, plus hub when the event came from a federated peer; the hub stamps id and time if you leave them blank. Fan-out never blocks: a subscriber that falls behind misses events instead of stalling everyone else.

Capabilities (RPC). The same socket carries request/reply. A provider registers method names; a caller calls them; the hub routes the call to whoever owns the method and the reply back, correlating by a global id:

provider → hub: {"op":"register","methods":["myplugin.lookup"]}
caller   → hub: {"op":"call","id":"req-1","method":"myplugin.lookup","params":{...}}
hub → provider: {"op":"call","id":"<global>","method":"myplugin.lookup","params":{...}}
provider → hub: {"op":"result","id":"<global>","result":{...}}
hub → caller:   {"op":"result","id":"req-1","result":{...}}

The router is single-owner per method, and a registration is released when its connection drops. Most methods a client calls (agents.spawn, agents.sendMessage, sessions.snapshots, sessions.conversation, claude.approve, claude.answer) are answered by the hub's own services, which take precedence over anything registered from outside. External providers add to that: a plugin sidecar answering methods in its own namespace, for example. The MCP facade is just another caller, re-exposing capabilities as MCP tools.

tokens

The bus is authenticated, and different credentials carry different provenance:

  • The host token lives at <configDir>/remote-token (24 random bytes, base64url, owner-readable). It identifies the machine's owner. If it goes missing from a directory that holds other state, serve refuses to mint a new identity unless you pass --allow-new-token.
  • Scoped tokens are minted with workspacer token create --scope view|triage|operator|provider and kept in tokens.json. View and triage are exact method allowlists that fail closed. Operator has the ordinary method surface but still not the host-only administration handlers. token list and token revoke manage them, and the bus revalidates open connections.
  • Per-session bearers are minted for each agent the hub launches so its tool calls carry its identity, and revoked when the session ends.
  • Per-plugin tokens identify each enabled plugin. Installing or reloading plugins needs the host token and answers 403 to every scoped one, operator included, because it runs code on the hub's machine.

<configDir> is $XDG_CONFIG_HOME/workspacer or ~/.config/workspacer on Linux and macOS, and %APPDATA%\workspacer on Windows. The native app's --local mode keeps its own copy inside its data directory instead.

Remote access is opt-in. A standalone hub listens on loopback until --host says otherwise. In the native app, Settings → Remote puts the hub behind Tailscale HTTPS for devices on your tailnet and creates pairing links at one of three access levels: read-only, triage, or full control.

shutdown and supervision

The hub supervises plugin sidecars (below) and nothing else: there is no sibling process to restart, because there are no sibling processes. An interrupt or SIGTERM to workspacer serve shuts the owned backend down, and a second signal may force the exit. The native app does the equivalent on Quit. A borrowed daemon (--external-claudemon) is left alive when the borrower exits.

how agents are driven

The hub launches four coding agents: Claude Code, Codex, GitHub Copilot and OpenCode. A spawn that names no provider gets Claude. A spawn that names pi is refused, because Pi's CLI has no MCP bridge and so cannot receive the work{spacer} tools every agent is given. The planning and launch code is services/hub-rs/src/services/{spawn_plan,agent_spawn,agent_lifecycle}.rs.

Who can start what depends on the client. The native app's New Agent offers Claude Code and Codex. All four are reachable through the agents.spawn capability and the spawn_agent tool, which is how an agent spawns a child on another provider.

two transports

A session is either a terminal or a managed stream.

PTY. The provider's own interactive CLI runs inside a pseudo-terminal the engine owns, and clients attach a terminal view to it.

Managed (stream). The engine drives the provider's machine interface and translates its events into one session model, so every provider shows the same things: mode, live conversation, usage, pending approvals and questions. There is normally no PTY.

The transport is the one the spawn asks for, else <provider>.transport in config.yaml. The shipped defaults are stream for Claude and Codex, and the native app always asks for stream. Every provider other than Claude is managed whatever the transport says.

How each provider is driven (services/claudemon/src/providers/):

  • Claude, managed (the default): the engine spawns claude --print --input-format stream-json --output-format stream-json (claude_stream.rs) and speaks the control protocol directly. Approvals and questions arrive as control requests; interrupts, model switches and permission-mode switches go back the same way. Stream sessions need no hooks.
  • Claude, PTY (claude.transport: pty): observed from the outside, through hooks that POST lifecycle events to the engine, the JSONL transcript under ~/.claude, and the status line. The hooks ride on each launch through --settings; nothing is written into your global Claude settings.
  • Codex: the engine runs codex app-server as a WebSocket daemon (codex app-server --listen ws://127.0.0.1:<port>, JSON-RPC 2.0) rather than over stdio. On stream it starts the thread itself (thread/start), sends each prompt with turn/start or steers a running turn with turn/steer, and consumes the notifications: turns starting and completing, items, streamed message deltas, token usage, and approval requests. On pty the session is a hybrid: the native Codex TUI runs in a terminal and creates the thread, and the engine finds it (thread/loaded/list) and rejoins it (thread/resume), so one conversation shows in both. A session-to-thread record under ~/.workspacer/codex-threads makes a session resumable after a restart. Codex reports tokens but not dollars, so cost is an estimate from a pricing table (session/pricing.rs, with your own rates in ~/.workspacer/model-rates.json).
  • OpenCode: the engine spawns opencode serve (HTTP, default 127.0.0.1:4096), drives a session over HTTP, and consumes the GET /event SSE stream. The translator is defensive: unknown event types and missing fields are ignored, not errors.
  • GitHub Copilot (beta): one copilot -p <prompt> --output-format json process per turn, read as newline JSON (copilot.rs). --session-id <uuid> both creates a session with that id and resumes one, so the engine pins its own id and every later turn rejoins the same conversation. -p mode cannot ask, so tools run without prompting and the choice is between directory-confined and --allow-all. Copilot bills in credits, so cost is an estimate here too.

Each adapter is a pure per-provider translator (native event → AgentUpdates, unit-tested) over a shared layer that folds updates into the session store. AgentUpdate is the common vocabulary: Idle, Busy, PermissionPending, AssistantText, UserText, ToolUse, ToolResult, Usage, Plan, Error and a few more.

Approvals and questions. A managed adapter parks the provider's request and surfaces it as a pending approval or question, and the answer you give is sent back to the agent. On Claude stream and Codex each card carries an id, and the engine refuses an answer addressed to a card other than the one on screen, so a late click can't land on a newer request.

Interrupt. On managed sessions an interrupt is structural, not a signal to a terminal: Codex gets turn/interrupt, OpenCode gets POST /session/:id/abort. The turn stops and the session stays.

what every agent is handed

Before a launch the hub checks that its MCP facade is ready, mints the session a bearer token, and injects the facade into the agent's MCP configuration. The agent gets the work{spacer} tools and every enabled plugin's tools. It also gets work{spacer}'s own skills, among them spawn-agent: written once to a content-addressed directory under ~/.workspacer/agent-skills and handed to that session only, as a plugin directory for Claude, as an extra skill root for Codex's app-server, and as a line of instructions naming each skill file for Copilot and OpenCode. Nothing is written into your project. The code is services/hub-rs/src/services/launch_instructions.rs and session_facade.rs.

writing a plugin

A plugin is a folder with a plugin.json manifest and, optionally, a sidecar process in any language. The hub loads <plugins-dir>/<name>/plugin.json, validates it, starts the sidecar, and announces it on the bus (plugin.loaded / plugin.unloaded). This section is the overview; the hands-on how-to (first plugin, manifest reference, bus protocol, hot-reload, publishing) is build a plugin.

what works where

The plugin system belongs to the hub, so a plugin's backend half works wherever the hub does, and its user-interface half only where a client draws it.

  • Everywhere the hub runs, including inside wks-native --local and under workspacer serve: the sidecar and its supervision, the capabilities it provides, the events it publishes and consumes, its settings, and its tools. Tools are the part an agent sees: every agent the hub launches is given the tools of every enabled plugin.
  • Only in the Electron app: panes, hotkeys, command-palette entries, the Plugins Manager, and theme injection into plugin webviews. The native app draws no plugin panes. A plugin that is only a pane has nowhere to appear there.

The plugins directory is <configDir>/plugins unless --plugins-dir says otherwise. For development, point a control plane at your own directory, or let the dev command build, load and reload one plugin as you edit it:

workspacer serve --hub-only --plugins-dir /absolute/path/to/plugins
workspacer plugin dev /absolute/path/to/my-plugin

the two kinds

  • Sidecar (server). Set server.command to a long-lived process. It connects to the bus itself, so it can run with no pane at all: react to events, answer capabilities, contribute tools. This is the kind that is useful with the native app.
  • Webview-only (ui). Set ui to a subdirectory of static assets and omit server. The hub serves the files at /plugins/ui/<id>/ for a client to show in an origin-isolated pane. Today that client is the Electron app.

the manifest (plugin.json)

The loader is services/hub-rs/src/plugins/manifest.rs. What it reads and enforces:

  • id and name. The id is letters, digits, ., _ and -, and it cannot claim a namespace the hub itself uses.
  • apiVersion, which must be "1".
  • server: command (required when server is set), args, port, and health (a path such as /health).
  • ui: a relative subdirectory of static assets.
  • provides: the capabilities the plugin answers. Each must sit in the plugin's own namespace: <id>.something, or <id>.*.
  • tools: MCP tools for agents. Each has a name (lowercase letters, digits and underscores), a description, a method that one of your provides entries covers, and optionally an inputSchema of type object.
  • settings: typed settings (boolean, number, string, select), scoped global or project. A secret must be a global string with no default.
  • install: a one-time setup argv run in the plugin directory after an install.

Anything else in the file (panes, hotkeys, capabilities, emits, consumes) is carried through for clients to use. Declaring panes with neither server nor ui is rejected, since nothing could serve them.

trust

Enabling a plugin trusts its code with your machine. There is no OS sandbox and no filesystem confinement: a sidecar and its install step run as you. The method and path lists a manifest declares are documentation and routing metadata, not grants. What is enforced is identity and provenance: each plugin has its own token, it can only register methods in its own namespace, host-owned topics and routes stay protected, archive extraction is guarded against path traversal, and installing or reloading requires the host token. Enable only plugins you trust.

the supervisor

src/plugins/supervisor.rs runs each sidecar. If the manifest gives a port and a health path it polls http://127.0.0.1:<port><health> every two seconds, with a 200 meaning healthy. An unexpected exit is restarted after a backoff that starts at one second, doubles to a thirty-second cap, and resets once the process has stayed up for thirty seconds. A stop sends SIGTERM on Unix and kills the process if it is still there five seconds later. Each change is published as sidecar.running, sidecar.healthy, sidecar.unhealthy, sidecar.crashed or sidecar.stopped.

bundled examples and the catalog

In plugins/examples/:

  • clock-plugin: the minimal sidecar. Start here.
  • headroom: a Node sidecar that contributes a launch integration, routing a session through a proxy you run.
  • editor and transcript-timeline: webview plugins, so they need the Electron app to be seen.

There is also a public catalog of install-ready plugins at workspacer-plugins. Read each one's manifest before assuming it suits the native app: the automations are sidecars, the dashboards are panes.

the mcp facade

services/hub-rs/src/mcp.rs exposes the hub's capabilities as MCP tools, so an agent, or any MCP client you configure, can see and drive every session. It is a thin adapter: a tool call becomes a bus call, the service that owns the method runs it, and the reply becomes the tool result. This is the mechanism under spawn-agent: the skill tells an agent how to use the spawn_agent tool, and the tool is one of these.

It serves two transports off one server: /mcp (Streamable HTTP, the current MCP HTTP transport) and /sse (legacy SSE), plus /health.

agents get it automatically

Every agent the hub launches receives the full tool set plus every enabled plugin's tools. Its bearer token (an Authorization header, or ?t= for clients that can only register a URL) supplies session identity and is revoked when the session ends; it is not a grant selector. The launcher verifies the facade is ready before minting that token, and a facade that is configured but cannot be verified refuses the launch rather than starting an agent with no tools. Older toolScope, plugin-selection and grant fields still parse and do nothing.

attaching your own client

With a standalone server the facade is at a fixed address:

# From the repository root; do not start beside an existing owner on these ports.
make build-cli
services/hub-rs/target/release/workspacer-rust serve
# Installed releases expose the same command as: workspacer serve

Mint the client a token first, since a caller with no credential is refused:

workspacer token create --scope operator --label "my mcp client"
{
  "mcpServers": {
    "workspacer": {
      "type": "http",
      "url": "http://127.0.0.1:7897/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}

Clients whose MCP registration is a bare URL and can't send headers append the token as ?t=<token> instead. View, triage and operator tiers apply to tokens you mint this way; they do not apply to the agents the hub launches. The native app's --local mode runs the same facade, but on a loopback port the OS assigns at startup, so 7897 is only the address of a standalone serve.

no credential, no tools

A request with no credential at all is refused with 401. The facade speaks plain HTTP on loopback, and loopback is reachable by every process and every user account on the machine (and by a container sharing the host network namespace), so "whoever reached the port" is not an identity. Before 0.160 it got the whole operator set; that is what changed.

The dial is facade.untokenedAccess in config.yaml (also serve --untokened and WKS_MCP_UNTOKENED), with three positions:

  • deny, the default. Credential-less requests get 401 on /mcp and /sse; /health stays open so liveness probes need no secret.
  • view. Credential-less requests get the read-only tier. No spawning or writing, but every session list and every transcript, to anything on the machine.
  • operator. Credential-less requests get everything. The pre-0.160 behaviour, kept as an explicit opt-in for a hand-configured local client that cannot carry a token.

Nothing work{spacer} launches is affected by any of the three, because every launched session carries its own token. The setting only governs callers that present nothing, and a token that is present but unknown or revoked is always 401.

the tools

The facade includes a help tool rendered from the live registry, and plugins contribute tools through their manifest's tools array. The initial plugin catalog is loaded before the facade reports ready; later changes are polled and apply to newly built catalogs. An MCP client that caches tools/list may need to reconnect, because there is no list-changed notification on this path.

  • list_agents, running agents with state, usage and pending asks.
  • spawn_agent, start a new agent on any of the four providers; returns its sessionId.
  • send_message, send a prompt to an agent.
  • get_transcript / get_conversation, read what a session has said and done.
  • approve, resolve a permission prompt.
  • answer, answer a question an agent asked.
  • signal, interrupt or stop a session.
  • create_terminal / terminal_input, open a shell and write to it.
  • notify, post a notification.

The rest cover snapshots (get_snapshot, list_snapshots), models and resumable sessions (list_models, list_resumable_sessions), config and profiles (get_config, reload_config, list_profiles), file and search access (read_file, write_file, list_dir, search_project), the project brief (brief_append), and more. services/hub-rs/assets/mcp-effective-tools.json is the authoritative list, by tier.

hub federation (hub-of-hubs)

A hub can link to named peer hubs and republish their sessions onto its own bus, so every client keeps its one connection while the agents span machines. The code is services/hub-rs/src/federation.rs; design notes are in docs/hub-federation.md.

  • Links are ordinary bus clients. Each peer in <configDir>/peers.json (name, url, token, and an optional dispatch flag) gets an outbound bus connection holding a scoped token the peer minted. The peer needs no concept of federation; the token's tier is the ceiling on the whole link. Tokens stay in that file, never in argv or config.yaml.
  • Events forward off an allowlist (agent.*, workflow.*, host.*, queue.*), stamped with the peer's name in the envelope's hub field. Payloads are never rewritten. Everything else stays home on purpose: a peer's layout.changed would clobber the local layout, and its command.* events would drive this machine's UI. An event that already carries a stamp is dropped, never forwarded again.
  • Calls qualify: hub:work/claude.approve forwards to peer "work", with a 25-second budget for an ordinary call. A scoped credential is checked against the bare method. Plugin identities stay local and cannot be used as federation credentials.
  • Dispatch is a separate opt-in. Linking a peer lets you see and drive its sessions. Letting this hub start new work on it needs dispatch set on that peer.
  • Reachability is first-class: hub.peer.connected and hub.peer.disconnected events let clients mark a peer's sessions as offline instead of losing them, and federation.peers (view tier) reports each link's state. Changing the peer list (federation.savePeersConfig) needs the host token and replaces the live links without a restart.
  • In the native app peers show up on the Hosts screen and in New Agent's Run on switch.
  • Try it on one machine: from the repository root, cargo test --locked --manifest-path services/hub-rs/Cargo.toml --test federation exercises isolated real hubs, forwarding and reconnect. This is a local contract test, not a cloud rollout.

the electron app

On its way out. The Electron app in apps/desktop ships alongside the native app in this release, and the next release deprecates it. New work goes into the native app. This section is here so the code stays explainable, not as a recommendation.

It is an Electron main process, a React renderer, and two child processes it supervises. Some things exist only here: tiled panes, the embedded browser, plugin panes and the Plugins Manager, the brief board, and the Fleet Manager launcher. The Fleet Manager is not being brought to the native app.

build and run

make install      # cd apps/desktop && npm install
make dev          # the app in dev mode, with hot reload
make dev-share    # the same loop with remote sharing forced on
./dev             # thin wrapper around npm run dev
make build-desktop
make package      # electron-builder installers, into apps/desktop/release/
make test-desktop # npm test

make install also runs electron-rebuild against better-sqlite3 so the native module matches your Electron version. make dev builds workspacer-rust and a release claudemon, builds the main process, starts the Vite renderer on http://localhost:5173, waits for it, then launches Electron. The Playwright suite (npm run test:e2e) is not part of make test.

GPU. Some Linux GPUs render the Chromium surface as speckled garbage, or crash Electron's GPU process on launch. make dev therefore sets WORKSPACER_DISABLE_GPU=1 by default, which calls disableHardwareAcceleration() and adds --disable-gpu-compositing. Run make dev WORKSPACER_DISABLE_GPU=0 to test real-GPU paths. None of this applies to the native app, which has no Chromium in it.

who spawns what

Electron main supervises two children:

  • claudemonDaemon.ts spawns claudemon serve --hook-port 7890 --api-port 7891.
  • hubDaemon.ts spawns workspacer-rust … serve --hub-only --external-claudemon …: the Rust hub as a control plane that borrows the engine Electron already started. Electron then registers its own desktop services with that hub.

In dev the binaries come from services/claudemon/target/release/claudemon and services/hub-rs/target/release/workspacer-rust; packaged, from <resourcesPath>/claudemon/ and <resourcesPath>/hub/. Before spawning, each supervisor probes the port's /health. A healthy service already there, such as a running workspacer serve, is adopted: no spawn, no supervision, never signaled on quit.

Owned children restart with backoff (RestartBackoff in lib/daemonUtils.ts): one second, doubling to a thirty-second cap, giving up after ten consecutive failures, with the counter reset once a child has stayed up for a minute.

remote sharing

Sharing is a runtime toggle in the app. WORKSPACER_REMOTE_SHARE=1 forces it on at launch (default bind 0.0.0.0:7895), and WORKSPACER_REMOTE_ADDR=host:port overrides the bind address, which is worth pinning to a tailnet IP. Both variables are read by Electron's launcher, not by the hub. When the built web renderer is present the hub also serves it at /app, which is this same React interface in a browser.

one agent, one card

The Electron and web clients mirror their layout through a hub-owned shared document, last writer wins. Two helpers in agentIdentity.ts keep that from multiplying cards: agentIdForSession(sessionId) derives the card id from the session id, so every client produces the same one, and dedupeBySessionId collapses any cards that still share a session whenever a layout is taken in. The native app has no layout document and does not take part in this.
